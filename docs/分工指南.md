# 《大数据技术基础》期末实验分工指南

## 1. 项目基本信息

- 项目仓库：[saymyzj/BUPT-BigData](https://github.com/saymyzj/BUPT-BigData)
- 推荐选题：基于爬虫与可视化的 A 股医药板块行情与舆情分析系统
- 研究方向：医疗与金融交叉场景
- 小组人数：3 人
- 主要交付物：
  - 研究实践报告
  - 课堂分享 PPT
  - 源代码压缩包
  - 数据文件压缩包
  - AI Agent 与 Skills 加分材料

## 2. 选题说明

本项目围绕 A 股医药板块上市公司，采集股票行情、行业指数、公开舆情或新闻标题等数据，完成数据清洗、统计分析、趋势分析、相关性分析、聚类分析和交互式可视化展示。

选题优势：

- 同时契合医疗与金融两大主题。
- 行情数据具有时间序列特征，适合做多角度分析。
- 医药板块股票数量适中，数据规模可控。
- 可视化展示空间较大，适合制作交互式 Dashboard。
- 适合拆分为数据采集、清洗分析、可视化三个可复用 Agent/Skill 工作流。

注意事项：

- 项目仅用于课程研究和数据分析展示，不构成任何投资建议。
- 不采集隐私数据，不绕过登录、验证码、付费墙等访问限制。
- 对有反爬机制的网站，应优先采用公开接口、低频请求、本地缓存和失败重试机制。

## 3. 小组分工

### 3.1 组长：爬虫数据采集与课堂汇报

对应评分项：

- 爬虫数据采集：5-7 分
- 课堂汇报：15 分钟以内 PPT 分享

主要职责：

- 调研并确定数据源。
- 获取医药板块股票列表、股票行情数据、行业指数数据。
- 采集少量公开舆情或新闻标题数据，作为舆情分析样例。
- 设计爬虫策略，处理请求间隔、失败重试、本地缓存和采集日志。
- 记录数据源链接、字段来源、采集范围和采集时间。
- 配合成员 B 完成原始数据交接。
- 负责最终课堂汇报。

不负责内容：

- 不负责数据清洗和预处理。
- 不负责主要数据分析建模。
- 不负责 PPT 制作。

可交付成果：

- 爬虫代码
- 原始数据文件
- 数据源说明
- 字段说明初稿
- 采集日志
- 反爬处理说明
- 爬虫运行截图
- 汇报讲稿或汇报提纲

Agent / Skill 加分材料：

- 数据采集 Agent 工作流记录
- 采集任务提示词或对话摘要
- 采集命令运行截图
- 原始数据生成截图
- 失败重试或缓存机制截图
- 人工审核说明
- 数据采集 Skill 或采集子流程说明

建议 Skill 名称：

- `stock_data_crawler_skill`

建议覆盖流程：

- 输入股票代码列表、起止日期、数据源配置。
- 自动采集行情、指数或舆情数据。
- 输出原始 CSV 文件和采集日志。

### 3.2 成员 B：数据清洗、数据分析、整体分析与 PPT 制作

对应评分项：

- 数据分析：1-3 分
- 整体分析：2-4 分
- PPT 制作

主要职责：

- 接收组长提供的原始数据。
- 完成数据清洗与预处理。
- 处理重复值、缺失值、异常值、日期格式、数值单位和字段命名。
- 建立清洗后的标准数据表。
- 完成描述性统计、时间序列分析、相关性分析、聚类分析。
- 完成舆情关键词或情绪分析。
- 提出至少 2 个创新且可落地的应用方向。
- 从技术可行性、成本效益、市场需求、数据可用性等方面完成整体分析。
- 制作课堂分享 PPT。
- 撰写报告中数据清洗、数据分析和整体分析部分。

可交付成果：

- 数据清洗脚本
- 清洗后数据文件
- 数据字典
- 分析脚本或 Notebook
- 描述统计结果
- 时间序列分析结果
- 相关性矩阵
- 聚类结果
- 舆情分析结果
- 整体应用价值分析
- PPT 文件

Agent / Skill 加分材料：

- 数据清洗与分析 Agent 工作流记录
- 清洗和分析任务提示词或对话摘要
- 脚本运行命令截图
- 清洗前后数据对比截图
- 分析结果文件截图
- 图表或统计结果截图
- 人工审核说明
- 数据清洗/统计分析 Skill 说明

建议 Skill 名称：

- `stock_data_analysis_skill`

建议覆盖流程：

- 输入原始数据文件。
- 自动完成去重、缺失值处理、字段标准化。
- 自动生成描述统计、相关性矩阵、聚类结果和分析结论草稿。
- 输出清洗后数据、分析结果和日志。

### 3.3 成员 C：数据可视化与加分材料汇总

对应评分项：

- 数据可视化：4-6 分
- AI Agent 与 Skills 加分材料汇总

主要职责：

- 基于成员 B 的清洗数据和分析结果搭建可视化页面。
- 制作 3-5 种不同类型的图表。
- 实现筛选、缩放、悬停提示、股票选择、日期范围选择等交互功能。
- 整理 Dashboard 页面截图和交互截图。
- 汇总三名成员的 Agent 使用记录、Skills 文件、运行日志和输入输出样例。
- 撰写报告中数据可视化部分和 AI 工具使用说明附录。

可交付成果：

- 可视化 Dashboard 代码
- 可视化页面运行截图
- 交互功能截图
- 图表说明
- Agent 与 Skills 加分材料目录
- 运行日志汇总
- 输入输出样例汇总

Agent / Skill 加分材料：

- 可视化 Agent 工作流记录
- 可视化页面生成提示词或对话摘要
- Dashboard 运行命令截图
- 图表生成截图
- 交互功能截图
- 人工审核说明
- 可视化生成 Skill 说明

建议 Skill 名称：

- `stock_dashboard_skill`

建议覆盖流程：

- 输入清洗后数据和分析结果。
- 自动生成图表配置或 Dashboard 页面。
- 输出可视化页面、图表截图和运行说明。

报告必须覆盖：

- 数据源选择理由
- 爬取策略

## 6. Git 分支协作规范

### 6.1 分支设计

用户要求采用 5 个分支。根据当前三人分工和“组长不需要个人分支，直接在 check 上开发”的规则，建议分支如下：

| 分支 | 用途 | 负责人 | 说明 |
| --- | --- | --- | --- |
| `main` | 最终稳定提交分支 | 组长维护 | 只存放最终确认后的版本，不直接开发 |
| `check` | 集成检查分支 | 组长主要开发 | 组长在此完成数据采集，并负责合并成员分支 |
| `member-b` | 成员 B 个人开发分支 | 成员 B | 数据清洗、数据分析、整体分析、PPT |
| `member-c` | 成员 C 个人开发分支 | 成员 C | 数据可视化、加分材料汇总 |
| `submit` | 最终提交归档分支 | 组长维护 | 从 `main` 创建，用于最终压缩包、报告、PPT、演示截图等提交材料归档 |

说明：

- 如果小组最终只希望保留代码协作分支，则核心开发分支实际为 `main`、`check`、`member-b`、`member-c` 四个。
- 为满足“五个分支”的要求，建议增加 `submit` 分支，专门保存最终提交状态。
- 组长不创建个人分支，直接在 `check` 上开发数据采集模块。

### 6.2 分支流转规则

推荐流转：

```text
member-b -> check -> main -> submit
member-c -> check -> main -> submit
组长开发 -> check -> main -> submit
```

规则：

- `main` 只接收经过检查的稳定版本。
- `check` 用于集成三名成员的工作。
- 成员 B 和成员 C 只在自己的个人分支开发。
- 组长在 `check` 分支开发和集成。
- `submit` 只在最终提交前创建或更新。

### 6.3 初始化分支建议

```bash
git clone https://github.com/saymyzj/BUPT-BigData.git
cd BUPT-BigData

git checkout main
git pull origin main

git checkout -b check
git push -u origin check

git checkout -b member-b check
git push -u origin member-b

git checkout -b member-c check
git push -u origin member-c

git checkout -b submit main
git push -u origin submit
```

### 6.4 日常开发流程

成员 B：

```bash
git checkout member-b
git pull origin member-b

# 完成数据清洗、分析、PPT 等工作后
git status
git add .
git commit -m "feat: add data cleaning and analysis workflow"
git push origin member-b
```

成员 C：

```bash
git checkout member-c
git pull origin member-c

# 完成可视化和加分材料汇总后
git status
git add .
git commit -m "feat: add dashboard and agent materials"
git push origin member-c
```

组长：

```bash
git checkout check
git pull origin check

# 完成数据采集工作后
git status
git add .
git commit -m "feat: add stock data crawler workflow"
git push origin check
```

### 6.5 合并规则

成员完成阶段任务后，不直接合并到 `main`，而是先合并到 `check`。

组长执行：

```bash
git checkout check
git pull origin check

git merge origin/member-b
git merge origin/member-c
```

合并后必须检查：

- 项目是否能运行
- 数据路径是否正确
- 报告和 PPT 是否能打开
- 可视化页面是否能启动
- 加分材料是否齐全

检查通过后再合并到 `main`：

```bash
git checkout main
git pull origin main
git merge check
git push origin main
```

最终提交前更新 `submit`：

```bash
git checkout submit
git pull origin submit
git merge main
git push origin submit
```

### 6.6 Commit 信息规范

Commit 信息采用如下格式：

```text
类型: 简短说明
```

常用类型：

- `feat`：新增功能
- `fix`：修复问题
- `docs`：文档修改
- `data`：数据文件更新
- `report`：报告内容更新
- `ppt`：PPT 更新
- `skill`：Agent/Skill 加分材料更新
- `refactor`：代码结构调整

示例：

```text
feat: add stock crawler for medical sector
data: add cleaned stock daily dataset
docs: update project division guide
skill: add data analysis skill usage logs
ppt: add final presentation draft
```

### 6.8 冲突处理规范

- 任何人修改前先 `git pull`。
- 成员 B 和成员 C 不直接修改组长负责的爬虫代码，除非提前说明。
- 组长不直接覆盖成员 B、成员 C 的代码，应通过合并和冲突解决保留双方有效修改。
- 报告和 PPT 容易冲突，建议约定由指定负责人集中修改。
- 大文件尽量避免频繁覆盖，必要时在文件名中加入日期或版本号。

### 6.9 禁止事项

- 禁止直接向 `main` 提交未检查代码。
- 禁止强制推送覆盖他人分支。
- 禁止提交账号、密码、Token、Cookie 等敏感信息。
- 禁止提交未说明来源的数据。
- 禁止采集需要登录、验证码、付费或明显禁止爬取的数据。
- 禁止在报告中夸大分析结论，例如直接宣称可以预测股价。

## 7. 阶段检查清单

### 第一阶段：数据采集完成

- 已确定数据源。
- 已保存源网站链接。
- 已生成原始数据。
- 已记录采集日志。
- 已说明反爬应对策略。
- 已向成员 B 交接字段说明和原始数据。

### 第二阶段：清洗分析完成

- 已完成去重、缺失值、异常值处理。
- 已生成清洗后数据。
- 已完成至少 4 种分析方法。
- 已生成分析结果文件。
- 已形成核心结论。
- 已完成整体应用价值和可行性分析。

### 第三阶段：可视化完成

- 已完成 3-5 种图表。
- 已实现筛选、悬停、缩放等交互。
- 已生成 Dashboard 截图。
- 已确认页面可正常运行。
- 已整理图表说明。

### 第四阶段：加分材料完成

- 三名成员均提交 Agent 工作流记录。
- 三名成员均提交对应 Skill 或子流程说明。
- 已提供运行日志。
- 已提供输入输出样例。
- 已提供截图。
- 已提供人工审核说明。

### 第五阶段：最终提交

- 报告完整。
- PPT 完整。
- 数据文件完整。
- 源代码完整。
- 加分材料完整。
- `check` 已合并到 `main`。
- `main` 已同步到 `submit`。
